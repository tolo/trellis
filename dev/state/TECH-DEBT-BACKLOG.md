| TD-006 | themes / trellis_css / trellis_site | Dart Sass 3.0 forward-compat: theme SASS and the `_theme_params.scss` bridge use `@import` (deprecated, removed in Dart Sass 3.0.0) — warn-only today (Dart Sass 1.x), will not compile on Sass 3.0. **This is a bridge REDESIGN, not a mechanical find-replace** (assessed 2026-07-06): the site-first param override works by generating `_theme_params.scss` (`$trellis-*: <merged> !default;`) and `@import`-ing it *before* the theme's `_variables.scss` in one global scope, so bridge values win over the theme's `!default`s. `@use` isolates/namespaces module scope, so this load-order trick doesn't survive — migration means (a) switching the bridge to `@use '<theme-main>' with (<all params>)` module configuration in `theme_sass_generator.dart` + the CLI wrapper (`build_command.dart` `_compileSass`), (b) making every theme's `_variables.scss` `@use ... with()`-configurable and each partial `@use 'variables' as *` (Arbor partials carry 100s of `$trellis-*` refs; Verdant similarly), and (c) re-testing the param-override + skin contract for both themes. Scoped as its own effort; do not bundle with unrelated work. The deprecated `if()` builtin in `arbor/sass/_variables.scss` was already modernized to `@if`. **Spec'd 2026-08-17**: `docs/specs/0.next-sass-use-migration/` (private repo – `prd.md` + `fis-sass-use-migration.md`), with the `@use ... with()` design verified by a throwaway SCSS spike rather than assumed. Sequenced AFTER `docs/specs/0.11/` (whose plan.json forbids touching the bridge) so the migration covers all six themes at once. Carries an open product decision (D2) the maintainer must settle before execution: today a forced skin defeats an explicit `theme_params:` colour override; under `@use` that precedence must be chosen deliberately. | Medium | docs-site |
| TD-011 | trellis_site | Theme SASS param values are not validated for structural CSS characters (`;`, `{`, `}`). `theme_sass_generator.dart` `_toSassValue` neutralizes SASS *interpolation* (`#{...}`, so it can't be evaluated — remediated in the 0.10.0 follow-up review), but a value carrying `;{}` still reaches the generated SCSS: a **string** value silently corrupts the output CSS (e.g. `content: a; } html { background: red;` closes the rule early and injects another), and a raw **color** value aborts the compile. **Scope — two sinks, values *and* names:** the same values also flow into the second emit sink `css/theme-props.css` (`_generateCssCustomProperties` / `_toCssValue`) — plain CSS copied verbatim to output with **no** compile gate, so corruption there is always silent (it never aborts). And it is not only param *values*: unknown site-override param **names** (`theme_params:` keys absent from the manifest) pass the merger warn-only and are emitted raw into **both** sinks, so a structural char in a key name has the same effect. A complete fix must cover both sinks and both values and names. Not a security boundary in the SSG model — params are build-time author config (theme.yaml / site `theme_params:`), not untrusted runtime input — so this is a robustness limitation (a typo produces broken output or a cryptic abort), not an exploit. Proper fix: a single value-validation/escaping policy across all param types (string/color/list/map) that either rejects structural chars with a clear `SiteConfigException` naming the param, or defines an explicit neutralization. Assessed as its own effort — do not bundle. Source: docs-site SASS remediation follow-up review 2026-07-07 (F-C residue). | Low | docs-site |

| TD-013 | trellis (FileSystemLoader) | Dev-mode template watching missed changes in **nested** template directories on Linux (`Directory.watch(recursive: true)` is inotify-backed there, and the `recursive` flag is silently ignored) | Medium | 0.10.1 | 2026-08-18 — fixed in `FileSystemLoader`. Audit first: `FileSystemLoader._startWatching` is the **only** directory watcher in the SDK (`rg "\.watch\("` over `packages/*/lib` otherwise finds only `ProcessSignal.sigint.watch()`); `trellis_dev` (`devMiddleware`, `liveReloadHandler`) and the `trellis serve`/scaffold dev flows all consume `loader.changes`, so the single fix covers every consumer. `trellis serve` serves built static output and watches nothing. Fix: on Linux the loader installs one non-recursive watch per directory, merged into the existing `changes` controller with the unchanged `path.endsWith(extension)` filter; watches are added for directories created or moved in later (the new subtree is scanned once and reported as a change when it already carries templates, since a directory can arrive populated before its watch exists) and dropped for deleted/moved-away ones; `close()` cancels all of them. macOS/Windows keep the single native recursive watch — behaviour and perf unchanged. No new dependency (`package:watcher` would add a runtime dep to the core engine and change event semantics on all three platforms for ~60 lines of logic) and no API change. The Linux `skip` on `file_loader_test.dart` "nested subdirectory file change detected" is gone and two tests were added (a directory created after watching starts is scanned *and* stays watched; `close()` silences nested directories too). Verified on macOS and on Linux in `dart:3.13` Docker: 25/25 green; mutation-tested by forcing the native-recursive path on Linux, where both nested tests time out deterministically. Three adjacent gaps found while closing this and fixed in the same change (all mutation-tested): the per-directory walk must be per-directory in its **error** handling too (one `listSync(recursive: true)` aborts the whole walk on an unreadable subfolder, escaping the constructor); a watch the OS refuses now warns once naming the directory and the inotify limit, rather than capping hot reload silently; and `close()` drops its controller before cancelling, since an event delivered mid-cancel could install a watch the shutdown snapshot no longer covered. `listTemplates()` also stopped following symlinks, so it no longer advertises names `load()` rejects (spurious `warmUpAll()` failures). |
| TD-007 | trellis_site | `_resolvePrevNext` recomputed `orderedSectionPages` per rendered single page – O(k·n log n) per section | Low→**Medium** | docs-site | 2026-08-17 — **fixed**, and the benchmark showed it was worse than filed. `benchmark/site_scale_benchmark.dart` (new) drove it at 100→8000 pages: on an evenly-spread docs site the quadratic term is invisible (5.8 ms at 1000 pages), which is what made it look benign – but the term is *per section*, so a flat single-section blog is the worst case, and there it **breaches the 5 s build NFR at ~4000 posts** (1000: 403 ms · 2000: 1.85 s · 4000: 8.4 s · 8000: 39 s).
